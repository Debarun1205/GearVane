Open source AI harness, MIT licensed

The AI coding harness that starts free.

Four models are ready the moment you install. Fifty more are one click away. GearVane classifies what you asked for, runs it through a tool-using agent loop with approvals and diff review, and picks the cheapest tier that can do the job. No account, no API key, and in Local-only mode nothing leaves your machine.

How it works

Three tiers, classified per request, with escalation on real failure rather than guesswork.

  1. 1

    Classify

    Keywords, files touched, error loops, and test failures are scored into a tier with a confidence you can inspect. Every decision shows its reasons.

  2. 2

    Run

    The cheapest tier that plausibly works runs first. Budget is checked before a single token is spent.

  3. 3

    Escalate when a cheap model cannot answer

    If the model errors, times out, or returns nothing usable, the failure is fed into the next decision and the task moves up a tier. Escalation is bounded, so a task that genuinely cannot be done will not march through every model in sequence.

    This is escalation on an error, not on a verified failure. GearVane does not yet run your tests to decide the answer is wrong; that is named work, not a current capability.

Tiers

GearVane runs the weights itself. Every model below is a file you download and run on your own machine, so a local run costs nothing and works offline.

local

free

Small weights, up to about 2 GB. Qwen, SmolLM2, Llama 3.2, TinyLlama, Phi.

  • Typos, formatting, renames
  • Small mechanical refactors
  • Boilerplate and documentation

mid

free

Mid-size weights, roughly 2 to 6 GB. Qwen 3, Mistral, Falcon3, DeepSeek R1 distills.

  • Multi-file changes
  • Adding an endpoint or a test
  • Edge-case reasoning

frontier

free

The heaviest local weights, over about 6 GB. Qwen 3 8B, Llama 3.3, DeepSeek R1 distills.

  • Architecture and design
  • Concurrency and debugging
  • Performance investigation

Read those names as size bands, not as a capability ranking. frontier means "the heaviest weights in the catalog" - an 8B model on your own hardware, not a hosted frontier model. Tiering by measured capability is not done yet, so the labels are provisional, and the app says so beside them. A benchmark that measures the tiers is on the list.

Hosted models are supported too, and they are the only tier that can cost you money: bring a key for Anthropic, OpenAI, Gemini, Mistral, xAI, DeepSeek, Groq, and others, and GearVane routes to them when a task warrants it. Local models carry no spend ceilings, because they cost nothing.

What this table does not tell you. The tier column is read from the router's own configuration, not calculated from the size - which is just as well, because size does not predict it. qwen3-8b sits in frontier at 4.7 GB while eleven weights under 2 GB sit in mid. The tier names are still provisional: a reasonable ordering, not a measured capability ranking, and a benchmark that would settle it is on the list. On the RAM figures. Where the Good for column mentions a number of gigabytes, that is hand-written guidance, not a computed requirement, and it does not hold together: a 15 GB weight claims 48 GB of RAM while an 18 GB one claims 32. Treat it as a hint to check against your own machine rather than a requirement. Tokens per second is absent entirely, because nothing measures it yet. Both become real fields when the hardware manager lands. Sizes are the on-disk download, so allow roughly the same again for memory while a model is loaded.

GearVane itself is MIT licensed. Each weight is downloaded under its own licence, and a few of those are custom rather than permissive - Meta's Llama, Google's Gemma, NVIDIA's Nemotron, Qwen, Falcon, DeepSeek, and BigCode all add terms. Only the Apache-2.0 and MIT weights ship in the installer; the rest are download-on-request, and the app shows the licence before you accept one. The full mapping is in THIRD_PARTY_NOTICES.md.

Inside the harness

Routing is the engine; this is the machine around it. A tool-using agent loop, review gates, and four surfaces running the same code - a chat box with a model behind it is not a harness.

Routing engine

Classify, run, escalate only on real failure. Every decision shows its reasons, and the budget is checked before a single token is spent.

Agent loop with tools

Read, write, edit, search, and run commands through a tool-calling loop with sessions, context budgets, repeat detection, and cancellation.

Desktop IDE

File tree, tabs, an integrated terminal, workspace search, a Problems tab, and a model picker covering every configured provider.

Ask and Build modes

Ask answers questions without touching files. Build runs the loop with write tools, and every file the run created or changed lands in a Review list where it opens as a side-by-side diff.

Prompt-driven building

Describe an app and get a scaffold from real templates, preview the files, and write them to disk - from the CLI, VS Code, or the IDE.

Ghost text

Inline completions from a local model through Ollama, local only by design: completions never go to a hosted provider.

Budgets and approvals

Per-task, per-session, and per-day spend ceilings, gated operations that require an explicit approval, and a set of commands that never run at all.

Reasons, not verdicts

Every routing decision lists the signals behind it - the keywords, the files, the confidence - so you can see why a tier was chosen and pin a different one. The learned classifier and its training loop exist and are tested in the CLI, and the desktop app does not yet record outcomes, so it does not learn from your runs yet.

Themes and onboarding

First-run onboarding, five dark themes, background ambience, accent colours, and a calm-motion mode. The look is stored per device, never in your config.

One engine, four surfaces: the CLI, the VS Code extension, the desktop app, and the Android build. Health checks probe your configured models from every surface that has a config.

Prefer to install from source?

The VS Code extension, the TypeScript CLI, and the Python package are all in the repository. 

git clone https://github.com/Debarun1205/GearVane
cd GearVane
npm install
npm run build --workspace @gearvane/core
npm run build --workspace @gearvane/cli
node packages/cli/dist/bin.js route --task "fix a typo"
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
pip install -e .
gearvane route --task "fix a typo"
cd apps/vscode-extension
npm install
npm run build
npx @vscode/vsce package
code --install-extension waypoint-0.3.0.vsix

These builds are not code signed. macOS Gatekeeper and Windows SmartScreen will warn on first launch, and the Android APK is debug-signed rather than Play-Store ready. Signing needs certificates that deliberately do not live in this repository. To get past the macOS warning, right-click the app and choose Open, or run xattr -d com.apple.quarantine /Applications/GearVane.app. On Windows, choose More info then Run anyway.

About GearVane

What this project is, how it is put together, and what it is not.

What it is

An AI harness built around a routing layer. It reads a request, classifies which tier can plausibly handle it, runs the cheapest one first, and escalates only when a cheaper tier actually fails - then hands the work to a tool-using agent loop whose changes you review as a diff. The point is not to be clever about which model to use; it is to stop paying frontier prices for work a free local model does perfectly well.

Why it exists

Teams buy a frontier model for everything by default, then discover that most of the traffic is typo fixes and lint cleanup. GearVane makes the cheap path the default and makes the expensive path something you have to justify by watching it fail first.

How it is built

The engine is written in TypeScript with no runtime dependencies, which is what lets the same code run in Node, in the browser, in Electron, and inside an Android webview without a Python runtime present. A Python implementation is kept in the repository as the reference, and a parity test asserts both route identically.

What it is not

It is not a model and it does not host one. It is not a sandbox: the safety layer gates destructive operations and asks for approval, but it does not contain them. It is not production-ready, and the learned classifier has never been measured against real traffic. See the known limitations.

FAQ

What makes it a harness and not a chat app?

A chat app hands your text to one model. GearVane classifies the task, routes it to a tier, runs it through a tool loop that can read, write, search, and run commands, gates destructive operations behind approvals, checks the budget before any token is spent, and shows the result as a diff you review. The chat box is one surface of that, not the product.

Do I need an API key?

Not to start. Install Ollama, pull a coder model, and GearVane routes everything local with no key at all. Add a hosted key only if you want the mid and frontier tiers available.

Where are my keys stored?

In your shell environment, and nowhere else. GearVane reads ANTHROPIC_API_KEY and similar variables, and never writes a credential to a config file, a log, or the dashboard. The desktop app additionally offers a Keys dialog, and its vault is encrypted by your operating system secret store - DPAPI on Windows, Keychain on macOS, libsecret or kwallet on Linux - so the file on disk is ciphertext only your login can open. Where the platform has no secret store the keys stay in memory for that session only, and the app says so rather than quietly writing plaintext. Entries are sent solely to their own provider. Local model servers are never sent a key at all.

Does it work offline?

With only the local tier configured, yes. Nothing leaves your machine. You can verify this by checking that no hosted provider is present in your config.

How accurate is the routing?

The heuristic classifier is deterministic and shows its reasons, so you can argue with it. Accuracy depends on your keywords and file patterns, which you control. Once you have recorded enough outcomes recorded through the CLI you can train the learned classifier, which refines the choice but always defers to the heuristic on disagreement. The desktop app does not record outcomes yet, so today it always routes on the heuristic.

What happens when a local model fails?

The failure is fed back into the next routing decision. After the configured number of consecutive failures the task moves up a tier. Escalation is bounded, so a task that genuinely cannot be done will not march through every model in sequence.

Can I control the cost?

Local models cost nothing per token, so a dollar ceiling on them would be meaningless; GearVane spends no budget on a local run. Hosted models are the ones that bill you, and for those it still supports per-task, per-session, and per-day ceilings, checked before tokens are spent, so a task that would exceed the limit is refused rather than truncated.

Can it push code or deploy for me?

The harness ships gating for those operations, but by default it will not act on your repository. Anything gated requires an explicit approval, and a set of commands such as rm -rf never run at all. GearVane does not sandbox execution, so treat approvals as you would treat running the command yourself.

Which providers are supported?

Anything speaking the OpenAI chat completions API: OpenRouter, Groq, Together, DeepSeek, Mistral, xAI, Meta, LongCat, Gemini, vLLM, LM Studio, llama.cpp's server, LocalAI, GPT4All, and oobabooga's text-generation-webui, plus hosted OpenAI itself. Ollama has dedicated support, and the Anthropic Messages API is supported directly. Local servers need no key; hosted ones read theirs from the environment, never from the config file.

Why both a Python package and a TypeScript one?

The Python package came first and remains the reference implementation. It cannot be bundled into an Android app, so the engine was ported to TypeScript with the same behaviour and its own test suite. The CLI, the app, and the VS Code extension all use the TypeScript engine.

Is it production ready?

No. It is alpha. The router, escalation, budget gates, and provider clients are tested end to end. The learned classifier trains and predicts but has not been evaluated against real production traffic, which is the obvious next step.

Does the Android build include the IDE?

Most of it, and the two gaps are real rather than oversights. The APK runs the same renderer in a webview, and the IDE mounts over a workspace kept in the app's own storage: the editor, file tree, search, and the Ask-mode agent all work, and files you create persist between launches. What is missing is the terminal, because a webview has no shell to run, and the file-changing Build mode, because the agent's tool layer needs Node and cannot load in a browser. The workspace README created on first launch says exactly this.
